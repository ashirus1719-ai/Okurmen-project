Система должна выглядеть не как обычный корпоративный сайт, а как **\*\*современный технологичный продукт\*\***, где движение интерфейса, фоновые эффекты, переходы, карточки, кнопки и переключатели создают ощущение живого приложения.

# 2. Технический стек и автономность

## 2.1. Базовый стек

Проект реализовать как единое production-ready веб-приложение:

- **Next.js** с App Router;
- **TypeScript**;
- **React**;
- **Neon PostgreSQL** как основная реляционная база данных;
- **Drizzle ORM** для типобезопасной работы с PostgreSQL;
- **Auth.js** для аутентификации и входа через Google;
- **Zod** для валидации входных данных;
- **React Hook Form** для сложных форм;
- **Tailwind CSS** для дизайн-системы и адаптивной верстки;
- **Framer Motion / Motion for React** для интерфейсных анимаций;
- **Lucide React** для всех UI-иконок;
- **Recharts** для административных графиков;
- **next-intl** или эквивалентная серверная i18n-архитектура для трех языков;
- **S3-совместимое объектное хранилище** для пользовательских файлов и медиа;
- серверные Route Handlers / Server Actions Next.js для backend-операций;
- PostgreSQL-транзакции для критических операций.

Конкретные версии пакетов фиксируются в `package.json` и lock-файле проекта.

## 2.2. Что означает «автономно»

Приложение должно быть функционально целостным и не зависеть от hardcoded/fake данных.

Обязательные правила:

- контент курсов, уроков, преподавателей, менторов, отзывов, событий, адресов и статистики берется из базы данных;
- пользовательские данные берутся только из базы данных текущего окружения;
- API не должен возвращать придуманные объекты, если запись отсутствует;
- отсутствие записи должно приводить к корректному `404`, `204` или Empty State;
- нельзя использовать массивы-заглушки в production-коде;
- нельзя подменять ошибку базы данных заранее придуманными данными;
- нельзя показывать «примерных» учеников, оплаты, отзывы или статистику как реальные;
- seed-данные разрешены только для локальной разработки и должны быть явно помечены как `DEMO`;
- demo-данные никогда не должны автоматически появляться в production;
- все изменения контента выполняются через админ-панель и сохраняются в PostgreSQL;
- бизнес-логика и проверки прав выполняются на сервере.

«Автономность» не означает отказ от внешних сервисов, которые необходимы для конкретной функции. Google OAuth, платежный провайдер, email, Telegram и объектное хранилище являются интеграциями, а не источниками фейковых данных. Если интеграция недоступна, интерфейс должен честно показывать ошибку или недоступность функции.

## 2.3. Архитектура

```text
Browser
   |
   v
Next.js App Router
   |
   +--> Server Components
   +--> Client Components
   +--> Server Actions / Route Handlers
   |
   +--> Auth.js + Google OAuth
   |
   +--> Service Layer
   |
   +--> Drizzle ORM
   |
   v
Neon PostgreSQL
   |
   +--> File Storage
   +--> Email provider
   +--> Telegram Bot
   +--> Payment provider
```

Нельзя переносить секреты, SQL, права доступа или критическую бизнес-логику в клиентский JavaScript.

## 2.4. Реальный источник данных

Для каждой сущности должен существовать определенный источник истины.

```text
UI
 ↓
Server Action / API
 ↓
Validation
 ↓
Authorization
 ↓
Service Layer
 ↓
Database
 ↓
Response
 ↓
UI
```

Если база не содержит нужной записи, приложение не имеет права самостоятельно придумывать ее содержимое.

**# 8. Аутентификация и Google Login

Основной способ входа должен поддерживать Google OAuth.

Требования:

- кнопка `Continue with Google` / локализованный вариант;
- OAuth выполняется только на серверной стороне;
- client secret никогда не попадает в frontend;
- после Google OAuth создается или связывается пользователь в PostgreSQL;
- повторный вход не создает дубликат пользователя;
- email Google используется для связывания аккаунта только согласно безопасным правилам провайдера;
- роли `ADMIN`, `MENTOR`, `STUDENT` хранятся в базе данных;
- права проверяются server-side;
- защищенные страницы дополнительно проверяют сессию и роль;
- `/admin` для пользователя без прав должен возвращать `403`;
- выход из аккаунта инвалидирует серверную сессию;
- cookies должны быть `HttpOnly`, `Secure` в production и иметь корректный `SameSite`.

Дополнительный парольный вход может быть добавлен только как отдельный явно реализованный способ. Нельзя оставлять форму регистрации без реально работающего backend-процесса.

**# 9. Три языка и локализация

Поддержать:

- Русский — `ru`;
- Кыргызский — `ky`;
- English — `en`.

Все пользовательские строки должны находиться в отдельных translation-файлах/ресурсах.

Пример:

```text
messages/
├── ru.json
├── ky.json
└── en.json
```

Нельзя:

- смешивать языки внутри одного интерфейса;
- заменять слова через `if` прямо в JSX;
- хранить переводы внутри компонентов;
- автоматически переводить контент базы данных без отдельного механизма локализации.

Для контента из базы данных использовать локализуемые поля или отдельные translation-таблицы.

Пример:

```text
courses
course_translations
lessons
lesson_translations
landing_sections
landing_section_translations
blog_posts
blog_post_translations
```

Язык пользователя хранится в профиле и/или cookie локали.

Переключение языка не должно терять текущий маршрут и параметры страницы.

**# 10. Иконки и визуальные элементы

Не использовать обычные emoji, текстовые смайлики или декоративные «стикеры» как UI-иконки.

Для интерфейса использовать библиотеку **Lucide React**:

```tsx
import { ArrowRight, BookOpen, User, Settings } from "lucide-react";
```

Разрешены:

- Lucide React;
- SVG-иконки из подключенной UI-библиотеки;
- собственные SVG, если они являются частью дизайн-системы;
- анимированные SVG через Motion.

Все иконки должны иметь единый визуальный стиль.

Не использовать emoji вместо:

- кнопок;
- навигации;
- статусов;
- достижений;
- статистики;
- действий;
- уведомлений.

Декоративные изображения и иллюстрации допустимы только как реальные загруженные ассеты или как явно обозначенные декоративные assets, а не как фальшивые фотографии людей.

**# 3. Главный анимированный фон**

**## 3.1. Фон лендинга**

Фон должен быть выполнен в стиле:

**\*\*black + white / dark + light + yellow accent\*\***

Основная идея:

- черно-белый динамический градиент;

- большие мягкие световые пятна;

- желтые светящиеся элементы;

- полупрозрачные пузыри;

- частицы;

- floating yellow balls;

- blur;

- glow;

- мягкое движение элементов.

**## 3.2. Желтые шарики**

На фоне периодически появляются желтые круглые элементы.

Поведение:

1\. появляются снизу;

2\. медленно поднимаются вверх;

3\. немного двигаются влево/вправо;

4\. меняют прозрачность;

5\. часть шариков увеличивается;

6\. часть уменьшается;

7\. некоторые исчезают за верхней границей;

8\. цикл запускается снова.

Эффект должен быть бесконечным.

Шарики не должны перекрывать текст.

**## 3.3. Дополнительные эффекты**

Можно использовать:

- glow;

- blur;

- noise;

- moving gradient;

- radial gradient;

- particles;

- glassmorphism;

- light beams;

- floating circles;

- animated lines;

- soft shadows.

**# 4. Hero-блок лендинга**

Главный экран должен занимать практически весь первый экран.

**## 4.1. Главный H1**

H1 должен автоматически менять текст примерно каждые **\*\*3 секунды\*\***.

Пример:

Важно: текст не должен резко прыгать при изменении длины. Высота блока должна быть зарезервирована.

**### Светлая тема**

- голубое небо;

- солнце;

- облака;

- мягкий фон.

**### Темная тема**

- ночное небо;

- луна;

- звезды;

- темный фон.

При переключении:

- солнце плавно превращается/уезжает;

- звезды становятся видимыми;

- фон плавно меняется;

- цвета интерфейса переходят без резкого переключения.

Настройка сохраняется в localStorage/профиле пользователя.

**# 81. Что нельзя делать**

Дополнительно строго запрещается:

- использовать hardcoded курсы, учеников, отзывы, платежи, команды хакатона или статистику в production;
- показывать fallback-данные при пустом ответе БД;
- выдавать demo-записи за реальные;
- создавать несуществующие даты, цены, рейтинги, результаты и достижения;
- использовать emoji как замену UI-иконкам;
- хранить Google OAuth secrets, DATABASE_URL, Telegram token и платежные секреты в клиентском коде;
- считать пользователя авторизованным только по данным из localStorage;
- проверять роли только на уровне интерфейса.


Нельзя:

- оставлять пустые страницы;

- использовать случайные fake testimonials как реальные;

- показывать admin navigation обычным студентам;

- доверять frontend для проверки прав;

- хранить секреты Telegram/payment в frontend;

- делать тяжелые бесконечные анимации без оптимизации;

- ломать интерфейс на мобильном;

- использовать разные стили кнопок в разных разделах;

- делать резкие переходы;

- создавать layout shift при смене H1.

# 91. Финальная архитектурная политика

Проект считается источником истины только в том случае, если данные подтверждены сервером и базой данных.

Приоритеты:

1. Реальные данные PostgreSQL вместо fake/fallback данных.
2. Server-side безопасность вместо визуального скрытия функций.
3. Google OAuth и надежная сессия вместо самодельной клиентской авторизации.
4. Три полноценные локали `ru`, `ky`, `en`.
5. Единая библиотека Lucide React вместо emoji и «стикеров».
6. Next.js App Router + TypeScript как основа приложения.
7. Neon PostgreSQL как основное хранилище.
8. Внутренний хакатон как полноценный модуль платформы.
9. Motion design как часть UI/UX, но с поддержкой `prefers-reduced-motion`.
10. Никакой выдуманной информации в production.

Любая функция, для которой в базе нет данных, должна корректно сообщать об отсутствии данных, а не создавать их автоматически.
